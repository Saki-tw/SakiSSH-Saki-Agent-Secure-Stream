### 2.1 ChaCha20 算力挑戰 (`challenge_store.rs`)

#### A. 現狀審查與安全裂隙 (Gaps)
1.  **金鑰疲勞與長期風險 (Key Fatigue)**：目前實作採用單一固定的隨機金鑰 `chacha20.key`。若 SASS daemon 長期不重啟，同一密鑰將加密數百萬個挑戰，極易觸發密碼學上的金鑰疲勞，並增加金鑰一旦在記憶體中洩漏後歷史流量被破解的風險。
2.  **O(n) 遍歷帶來的 DoS 脆弱性**：由於 `ChallengeRequest` gRPC 協議尚未包含 Nonce 欄位，SASS 必須在 `try_verify_any` 中遍歷所有 pending 挑戰。若受控 Agent 發起數十萬次 Fake Responses 進行高頻碰撞，會將遍歷複雜度推高至 O(n)，反向耗竭 SASS 的 CPU。

#### B. 架構完善與被接受機率優化 (IETF & 學術)
*   **金鑰輪轉機制 (Key Rotation)**：引入「Epoch 滑動視窗」。系統每 3600 秒（1 小時）自動輪轉一次 ChaCha20 Key，且記憶體中僅保留 `Current_Epoch_Key` 與 `Previous_Epoch_Key`，提供完善的前向安全與密碼學強度。
*   **O(1) Adjudicator 協議修正**：在 `sakissh.proto` 協議的 `ChallengeRequest` 中強制新增 `challenge_nonce` 欄位。SASS daemon 接收後直接以 $O(1)$ Hash Map 檢索，拒絕任何遍歷，徹底防範算力耗竭型 DoS。

---

### 2.2 焦油坑 active defense (`tarpit.rs`)

#### A. 現狀審查與安全裂隙 (Gaps)
1.  **TCP Window-Clamp 網絡級逃逸 (側信道)**：目前實作僅依靠 3 秒的 `send timeout`。受控 Client（或具有網絡層控制權的 Agent）可以故意將 TCP 接收視窗限制在極小狀態（例如僅 1 字元），並每 2.9 秒讀取一次。這將持續重置 timeout 計時器，使 40MB 的發送進程被拖長至數天，成功卡死 SASS 的並行線程，規避 AtomicI32 門控。
2.  **ANSI Vi-Swap 之靜態性**：Vi-swap 的 `:qa!` 偵測是硬編碼的，聰明的 Agent 很快就能通過分析 ANSI buffer 的特徵碼（如特定的 tilde 序列）識別出自己處於虛擬沙盒中，進而放棄交互進行隱蔽逃逸。

#### B. 架構完善與被接受機率優化 (學術)
*   **字節級動態流量整形器 (Traffic Shaping Tarpit)**：摒棄單純的 timeout 依賴。SASS v2.0 引進基於 Token Bucket（權杖桶）的速率限制器，將發送速率主動強制鎖定在 $256 \text{ bytes/sec}$。無論 Client 的 TCP window 如何抖動，SASS 均在 Transport 層主動限速，完成對 Agent Token 預算的主動物理耗竭。
*   **動態混淆 ANSI 界面 (Polymorphic Vi-Swap)**：在模擬 Vi 界面時加入「多態混淆機制」，動態隨機化警告文字的 ANSI 顏色、tilde 的隨機間距以及狀態列的標題，打碎特徵碼，讓 Agent 在檢索畫面時無法通過正則判定自己是否處於蜜罐。

### 2.3 Micro Branch 透明分流 (`branch_mgr.rs`)

#### A. 現狀審查與安全裂隙 (Gaps)
1.  **UVSF Symlink Race / ToCToU 越權漏洞**：這是 userspace 模擬檔案系統（UVSF）最致命的軟肋。當 SASS 將 Agent 的寫入分流至 Symlink Tree 後，Agent 在執行指令時可以通過高頻的併發進程，刪除某個 symlink 節點，並建立一個指向 Host 真實敏感目錄（如 `/etc/pam.d` 或 Windows 的啟動資料夾）的惡意連結。SASS Daemon 若在 `realpath` 解析時與命令執行存在時間差（ToCToU），就會發生越權寫入，導致 Host 徹底被劫持。

#### B. 架構完善與被接受機率優化 (IETF & 學術)
*   **實時解析路徑守衛 (Safe Path Resolution Guard)**：在 `build_symlink_tree` 與 process spawn 前，SASS v2.0 引進實時的邊界守衛。所有文件路徑解析必須在核心態（或使用 `O_NOFOLLOW` 標記）進行。利用 `realpath` (Unix) 或 `GetFinalPathNameByHandle` (Windows) 對解析後的實體目標路徑進行檢索，強制執行邊界判定：
    $$\text{ResolvedPath} \subseteq \text{BranchSandboxPath}$$
    一旦檢測到任何路徑試圖跨越沙盒邊界，立刻觸發 R6 (DROP) 零容忍斷開，徹底消滅 Symlink Race。

### 2.4 環境注入防禦 (`env_injector.rs`)

#### A. 現狀審查與安全裂隙 (Gaps)
1.  **作業系統不敏感引發之 Cascading Failure**：如 U9 Host 的 Cascading Failure 事件，預設清洗 PATH 會剝奪 Windows 調用核心系統 DLL (`vcruntime140.dll`) 的權利，引發合法 ASR 字幕管線的靜默崩潰，構成「自我誘發的遙測與執行中斷（self-inflicted pipeline disruption）」。

#### B. 架構完善與被接受機率優化 (IETF & 學術)
*   **OS-Aware 平台 Profile 標準化**：在 `EnvInjector` 中實施「作業系統架構感知」策略。
    *   **Windows 專用 Profile**：自動將 `SystemRoot`、`windir`、以及 `%System32%` 保留在環境變數白名單中。
    *   **靜態連結編譯推薦規範**：將靜態連結標籤（`+crt-static`）寫入 SASS 協議規範。
    這在安全隔離（Defense-in-Depth）與運維摩擦（Operational Friction）之間取得了數學上的最優平衡點。

---

### 2.5 區塊鏈式審計鏈 (`audit.rs`)

#### A. 現狀審查與安全裂隙 (Gaps)
1.  **本地金鑰單點失效與 MITM 篡改**：雖然審計日誌使用本地 Ed25519 金鑰簽署，但如果 SASS daemon 本身在運行期遭遇內存提取，或是 Host OS 被最高權限入侵，入侵者可以獲取 `audit_key.pem`，隨後對修改後的 `audit.jsonl` 日誌重新進行 Hash Chaining 簽名。這會使鏈式防護在面對「Root 級惡意 Agent」時，因公鑰在本地獲取而失去可信度。

#### B. 架構完善與被接受機率優化 (IETF & 學術)
*   **外部飛地/時間戳雙重錨定 (Dual-Attestation & Ledger Anchor)**：
    *   SASS v2.0 不再僅僅依賴本地簽名。
    *   **外部推播（Push-to-Enclave）**：每當 Hash Chain 產生新的 Block Hash，SASS daemon 會非同步將此 Hash 及其簽章外推至一台物理隔離的外部 Syslog 服務器或將其寫入 macOS 晶片的 Secure Enclave / Windows TPM。
    *   這使得任何本地日誌篡改，都會因為與外部 Enclave 的 Hash 記錄不匹配而當場暴露，達成了真正的前向安全防護。
